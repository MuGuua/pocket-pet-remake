# 口袋精灵联机复刻版架构草案

## 目标边界

第一版只解决 4 个核心问题：
- 登录与实时连接
- 世界状态同步
- 宠物养成与编队
- 服务端权威战斗与结算

第一版明确不做：
- 公会、交易行、邮件、排行榜
- 跨服与多进程拆分
- 实时 PvP
- 开放世界实时技能战斗

## 总体架构

- 客户端：Godot 4 + GDScript
- 服务端：Go 单体服 + WebSocket + HTTP
- 通信：`HTTP(S)` 登录，`WSS` 实时消息，消息体使用 `Protobuf`
- 持久化：PostgreSQL
- 短时状态：Redis

## 设计原则

- 客户端负责表现、输入、UI，并自主决定普通同场景移动位置
- 服务端负责传送与切图判定、同步广播、战斗结算和其他玩法结果
- 普通同场景移动直接上报客户端当前位置；传送、战斗等影响玩法结果的动作仍只上报意图
- 世界同步和战斗同步分离，分别维护自己的状态版本号

### 同场景玩家移动同步
- 客户端直接完成本机普通移动，不等待服务端许可，也不接受服务端坐标纠偏；移动期间以 100ms 最小间隔单向上报当前位置和远端表现状态。
- 每次上报通过 `MOVE_INTENT_REQ` 携带整数格 `target_pos`、千分之一格 `precise_pos`、四方向 `facing`、`moving` 和递增 `move_seq`；服务端不计算速度、边界、导航或最终落点。
- 服务端只校验当前会话、场景和严格递增序号，通过 Redis CAS 防止旧包覆盖新包；旧会话、错误场景、重复/倒退序号和短时仓储异常均静默丢弃，不向本机发送 `MOVE_INTENT_RESP` 或 `WORLD_RESYNC_PUSH`。
- 成功记录后，服务端仅向同场景其他在线玩家发送 `ENTITY_MOVE_PUSH`；该消息用于远端人物和宠物表现，不是对移动者本机的权威回包。
- Redis 保存客户端最近上报的高精度在线位置，dirty worker 按位置版本异步写回 PostgreSQL；停止、切图、战斗、断线、顶号和停服等关键节点继续触发最终写回。
- 玩家进入世界、切换场景和断开连接时，服务端分别发送 `ENTITY_ENTER_PUSH` / `ENTITY_LEAVE_PUSH`，客户端据此创建或移除远端角色。
- 正式登录、普通门和世界地图快速传送的唯一人物落点均来自服务端权威快照 `self_pos`；客户端完成目标地图加载后只把服务端场景坐标转换为 Godot 像素坐标并显示。场景脚本中历史遗留的 `login_and_map_teleport_spawn_position`、`portal_spawn_scene_positions` 和 `get_portal_spawn_scene_position()` 不再参与运行时权威落点链路；旧客户端跨场景请求携带的 `target_pos` 继续被服务端忽略。
- 玩家实体摘要携带数据库编队首只宠物的 `following_pet`；客户端为远端角色创建独立 Y-Sort 跟随节点，玩家更换编队后服务端向同场景其他玩家广播实体刷新。
- 客户端远端角色只负责插值和动画展示，不启用输入、相机或碰撞；创建与刷新时都会应用实体摘要中的服务端 `skin_id` 人物形象，重新进入世界时以服务端快照中的在线玩家列表重建。
- 远端人物直接使用服务端归一化朝向和起停状态，不再根据延迟坐标猜方向；两个 100ms 移动包之间按人物速度短时连续预测，并在新包到达后平滑纠偏，预测最多持续 180ms，断包后不会无限前进。远端插值保留连续浮点坐标，像素吸附只发生在渲染层，避免逐帧取整造成的阶梯抖动。
- 远端宠物按高精度人物轨迹重新累计 24px 路径步，转向时重置路径轴并使用与本地宠物一致的移动速度。

### 场景切换关键路径

- 切图校验只读取玩家等级、当前场景、位置和位置版本，不进入完整玩家档案、装备或战斗快照重算链路。
- Redis 已启用时，handler 复用已经读取的移动状态执行序号 CAS，切图预留序号由原来的重复读取收敛为一次 `GET + CAS`；场景与位置仍按现有位置版本规则同步写入 PostgreSQL，不改变持久化一致性。
- 客户端发起传送请求后立即通过 `ResourceLoader` 线程预加载目标地图；黑屏中点优先消费预加载结果，失败时才回退同步加载。
- `scene_loaded` 仅表示地图、人物、权威落点、相机等视觉关键内容已就绪，可以结束黑屏；导航网格在场景可见后每帧最多扫描 64 格，完成后发出 `scene_runtime_ready`。导航构建期间暂时禁用点击寻路和暗雷步数判定，人物手动物理移动不受影响。
- 远端玩家实例化和宠物跟随补齐不再阻塞 `scene_loaded`；服务端跨场景快照可先省略在线玩家，再用现有实体进入推送补齐，不新增协议字段。

### 在线移动同步运行态

- 多人同屏移动优化清单统一维护在 `backend/docs/multiplayer-movement-optimization-plan.md`。
- `world.MovementStateRepository` 是领域层的短时在线移动状态边界；Redis适配器通过应用装配注入，WebSocket handler 不直接依赖 Redis客户端。
- Redis玩家移动状态使用 `{key_prefix}:world:movement:player:{player_id}`，保存会话、场景代次、千分之一格定点坐标、移动序号和位置版本，TTL 为 24 小时并在更新时续期。
- 状态更新使用 Lua CAS，同时比较会话、场景代次和旧移动序号；成功更新后把玩家加入 `{key_prefix}:world:movement:dirty`。批量持久化入口使用 Redis `SPOP key count` 原子领取一批玩家编号，领取后发生的新移动会再次 `SADD`，不会被旧批次成功处理误删。
- 应用层周期写回 worker 通过 `world.Service` 领取 dirty 玩家并读取 Redis 最新权威状态，再通过 `player.Service.UpdatePositionIfNewer` 把场景、整数坐标和 `position_version` 条件写入 PostgreSQL。默认每 5 秒最多处理 100 名玩家，周期与批次上限由 YAML `movement_persistence` 配置；批次串行执行，单玩家失败不阻断同批其他玩家，读取或数据库错误的编号在批次末统一重入队。数据库已有相同或更高版本时按 stale 安全跳过，不覆盖新位置且不重试。
- 已于 2026-08-17 执行的迁移 `123_player_position_version.sql` 定义了玩家表的非负永久位置版本字段。普通档案与战斗快照查询都会读取该字段；首次进入世界或 Redis 状态缺失时，以 PostgreSQL 快照及其版本初始化 Redis，避免缓存重建后从零重新计数。同一会话重复进入不会重置移动序号，新登录会话可以替换旧状态。切图成功时以 `max(Redis 版本, PostgreSQL 版本) + 1` 构造目标场景状态，先条件写入 PostgreSQL，再使用同一版本重建 Redis 场景代次，避免新旧存储出现版本倒退。
- 普通同场景移动的正式调用链为：WebSocket 协议解析 -> `world.Service.MovePlayer` -> Redis 在线状态加载 -> 玩家/会话/场景校验 -> 客户端坐标与表现字段记录 -> 移动序号校验和 Redis Lua CAS -> 仅向同场景其他玩家广播。普通移动不调用 `EvaluateMovement`，handler 不发送成功或拒绝响应。
- `MovePlayer` 返回上报前后的在线状态：上报前状态用于远端广播起点和识别停止事件，上报后状态用于远端广播与持久化。Redis 已启用时，普通移动 handler 不再同步查询 PostgreSQL 档案或逐包写入位置；Lua CAS 更新成功后只标记 dirty，由周期 worker按版本异步写回永久位置，旧批次不能覆盖相同或更高版本。由移动切换到停止时，handler 在广播后异步触发最终写回；写回入口会重新读取 Redis 最新状态，避免停止包之后的新移动被旧坐标覆盖。未装配 Redis 的旧服务兼容分支仍读取并同步写入 PostgreSQL，但也不回包纠正客户端。
- 同会话重连优先用 Redis最新场景、整数位置和千分之一格位置重新查询场景快照；缓存缺失时回退 PostgreSQL并重建 Redis状态，客户端通过可选 `self_precise_pos` 恢复高精度位置。
- 普通移动、普通门和地图快速传送共享严格递增的 Redis移动序号；跨场景成功后以目标场景版本重建状态，旧场景或重复请求不能再次执行传送。
- PVE 交互、野外遭遇、NPC 配置战斗和 PVP 接受仍会在创建战斗前同步保存 Redis 中最近上报的位置，用于永久档案一致性。客户端在收到战斗开始事件时单独记录当前本地场景坐标，离开战斗后优先恢复这份本地记录；记录缺失或场景不匹配时使用当前地图 `get_login_and_map_teleport_spawn_position()` 的传送出生坐标。新客户端忽略战斗结果中的服务端 `return_pos`。
- 普通断线先同步写回最终位置，再执行战斗托管处理与世界离场广播；新登录顶号在会话锁外先写回旧会话位置，再通知并关闭旧连接，普通重连不会误触发顶号写回。
- 优雅停服先停止 HTTP 接入，并由 WebSocket Hub 拒绝新连接、关闭现有连接、等待读取循环、当前消息处理和断线回调结束；随后停止周期 worker，在 5 秒窗口内排空 dirty 集合，最后关闭 Redis 与 PostgreSQL。排空失败的玩家在本轮结束后统一重入队，避免数据库持续失败时无限重复领取。
- P1-08 的关键节点最终写回已经闭环；P1-09 的 Redis 断开、PostgreSQL 短时失败、重启恢复和旧版本覆盖完整故障测试仍待完成。
- 同场景移动广播携带移动后 Redis 状态中的真实 `scene_version`，同地图快速传送广播携带传送决策中的场景代次；未装配移动状态仓储的旧服务兼容分支保留零值，不再使用固定场景代次。
- 客户端 `GameState` 按远端实体维护最近接受的 `scene_id + scene_version + move_seq`，只把严格更新的同场景包交给世界控制器刷新目标位置；旧代次、同代次重复/倒退序号、跨场景包和离场延迟包不会改写实体快照或重新创建幽灵实体。全量世界快照与实体离场负责清理基线，编队/形象摘要刷新复用实体进入推送时保留既有移动基线。
- `world_movement_config`、场景矩形边界、发布导航位图、`EvaluateMovement` 与对应后台维护能力作为历史权威移动能力继续保留，避免扩大本次改动；它们不再参与普通同场景移动计算或本机纠偏。
- 服务启动和后台更新仍沿用既有移动配置、边界与导航缓存装配流程；后续若要删除这些能力，应作为独立清理任务核对传送、出生点审计、后台权限和迁移兼容性。
- 场景矩形外边界存放在 PostgreSQL `world_scene_definition.boundary_*_milli` 字段中，使用千分之一场景格闭区间；已于 2026-08-17 执行的迁移 `119_world_scene_boundaries.sql` 为现有 1~26 号场景初始化边界，并要求未来新增场景同时提供合法边界。
- 服务启动时仍通过 `world.SceneBoundaryRepository` 加载全部启用场景边界到 `world.Service` 只读缓存；缺失、重复或非法矩形会阻止服务启动，但普通同场景上报不读取该缓存。
- 运营后台通过 `GET /api/admin/world/scene-boundaries` 和 `PUT /api/admin/world/scene-boundaries/{scene_id}` 维护完整矩形；接口复用 `world_movement:view/edit` 权限，更新要求操作原因，写库成功后原子替换对应场景运行时快照。
- `world_scene_navigation` 保存每张场景版本化的静态通行位图，当前已发布版本是精细墙体和装饰阻挡判定的事实来源；`119_world_scene_boundaries.sql` 继续只负责场景外围矩形，`120_world_scene_navigation.sql` 建表，`122_world_scene_navigation_seed.sql` 写入 1~26 号场景首批发布数据，上述迁移均已于 2026-08-17 执行。
- 静态通行数据链路为：Godot 正式地图静态碰撞与玩家碰撞体 -> `client/tools/export_scene_navigation.gd` -> 待执行迁移 SQL 或后台草稿 -> PostgreSQL 发布版本 -> 服务启动只读缓存。当前普通同场景移动不再使用服务端位图逐格裁剪，客户端按本地地图碰撞完成移动。
- 服务启动必须为全部启用场景加载唯一有效的发布位图；缺少导航、位图非法、起点位于阻挡格时失败关闭。后台发布或回滚成功后，当前进程立即以深拷贝替换对应运行时缓存，后续移动不需要重启即可使用新版本。
- 普通同场景移动不再执行服务端速度、矩形边界、静态通行、斜向输入拒绝或分级纠偏；客户端发送成功后立即更新本地上报基线，不维护普通移动请求在途状态。
- `MOVE_INTENT_RESP` 和 `WORLD_RESYNC_PUSH` 继续用于传送门、地图快速传送、跨场景切换、登录和重连，这些流程仍由服务端决定场景与落点。
- 服务端默认出生点、普通门目标点和数据库快速传送中心都必须位于对应场景的已发布可通行格；客户端不再使用本地导出变量覆盖这些权威位置。

## 强约束

- `transport -> module -> data` 单向依赖
- `ws handler` 不直接写业务逻辑
- UI 不直接发送网络包，统一通过控制器或网络层
- 战斗结果只看服务端推送
- 普通同场景本机位置以客户端本地移动为准；传送、切图、登录和重连落点以服务端快照为准

## 系统名称富文本契约

- 数据库配置的物品、装备、宠物模板、技能、怪物、NPC、任务等系统展示名称允许保存 Godot BBCode。
- 后台统一使用富文本编辑器录入系统展示名称；客户端使用 `RichTextLabel` 渲染服务端原文。
- 玩家名与玩家自定义宠物名始终是纯文本。即使承载节点是 `RichTextLabel`，也必须先按纯文本转义后展示。
- 业务判断、关联、搜索键和数值计算必须使用稳定 ID、code 或显式配置，不得依赖带格式的展示名称。
- 当前名称编辑器支持 `[color]`、`[b]`、`[i]`、`[u]`，不要在名称中使用图片、链接或影响移动端布局的标签。
