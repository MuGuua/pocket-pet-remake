## 1. 文档目的

本文档用于指导 `pocket-pet-remake` 多人同屏移动链路的持续修复与优化，并作为开发过程中的唯一执行清单。

## 2. 当前问题

当前多人同屏已经支持同场景玩家进入、离开、移动广播，高精度表现坐标、四方向朝向、起停状态、远端短时预测以及平滑追赶。

当前需要继续解决以下问题：

- 普通移动已经解除单请求在途限制，但仍需在真实弱网和移动设备上验证定频上报、转向、停步和断流表现。
- `move_seq`、`scene_version` 与 Redis CAS 已形成防旧包覆盖链路，仍需补 Redis 断开、PostgreSQL 短时失败和重启恢复测试。
- PostgreSQL 已移出普通移动实时广播关键路径，仍需持续验证停止、战斗、断线、顶号和停服节点的最终写回可靠性。
- 远端角色只追赶最新目标点，没有基于服务端时间的快照插值。
- 当前广播范围是整张场景，不是真正的网格 AOI。

## 3. 目标架构

```text
客户端本机自主移动
    -> WebSocket 单向坐标上报
    -> world 领域服务校验会话、场景和序号
    -> Redis 原子更新最近上报状态
    -> 服务端仅向其他玩家广播移动状态
    -> 远端玩家快照插值
    -> 定时或关键节点批量持久化 PostgreSQL
```

职责边界：

- 客户端负责普通同场景移动、碰撞、动画和当前位置上报，不等待普通移动回包。
- `ws` handler 只负责协议解析、调用领域服务和向同场景其他玩家广播；普通移动不发送响应。
- `world` 领域服务负责玩家、会话、场景和序号隔离，不计算普通移动速度、边界或通行结果。
- Redis 保存在线玩家最近上报的移动状态和待持久化标记。
- PostgreSQL保存永久位置、地图通行配置和版本数据。
- 传送门、地图快速传送、跨场景切换、登录和重连仍由服务端决定场景与落点。

## 4. Redis运行态设计

### 4.1 Key

所有 Key 必须复用现有 Redis `key_prefix`：

```text
{prefix}:world:movement:player:{player_id}
{prefix}:world:movement:dirty
{prefix}:world:scene:{scene_id}:players
```

第一阶段只实现玩家移动状态和 dirty 集合；场景在线索引在 AOI 阶段接入。

### 4.2 玩家移动状态

```json
{
  "player_id": 10001,
  "session_generation": 8,
  "scene_id": 3,
  "scene_version": 12,
  "precise_x": 12310,
  "precise_y": 8000,
  "persisted_x": 12,
  "persisted_y": 8,
  "facing_x": 1,
  "facing_y": 0,
  "moving": true,
  "speed": 90,
  "last_move_seq": 302,
  "last_server_tick": 92001,
  "position_version": 1502,
  "dirty": true
}
```

坐标使用千分之一场景格定点整数。Redis 状态设置过期时间并在活跃期间续期，但 TTL 只负责回收，不代替 PostgreSQL持久化。

状态更新必须使用 Lua 或等价的 CAS 操作，至少比较 `session_generation`、`scene_version` 和 `last_move_seq`，禁止使用非原子的 `GET` 后 `SET` 覆盖。

### 4.3 Redis故障策略

- Redis不可用时，不静默切回每个移动包写 PostgreSQL。
- 普通移动上报发生 Redis 错误时只记录日志并丢弃该包，不向本机发送拒绝或坐标纠正；客户端继续本地移动，后续上报可重新建立在线同步。
- 切图、进入战斗、顶号和正常停服前必须尝试把最终状态写回 PostgreSQL。
- PostgreSQL短时失败时保留 dirty 标记并重试，不删除 Redis状态。

## 5. 协议演进

### 5.1 `MOVE_INTENT_REQ`

保留现有字段：

- `target_pos`：客户端当前整数场景坐标，服务端记录后供远端同步和持久化。
- `precise_pos`：客户端当前千分之一格表现坐标，服务端原样记录和广播。
- `input`：四方向移动表现兼容字段，不参与服务端普通移动计算。
- `client_tick`：客户端单调时间，仅用于延迟诊断，不参与权威计时。

普通同场景请求为 fire-and-forget；旧会话、错误场景、重复/倒退序号和仓储错误均静默丢弃。

### 5.2 `MOVE_INTENT_RESP`

该消息只用于传送门、地图快速传送和跨场景切换。以下普通移动纠偏字段作为旧协议兼容保留，新客户端不再消费：

- `corrected_precise_pos`：服务端最终高精度权威位置。
- `server_tick`：服务端生成权威结果的时间基线。
- `speed`：旧版服务端权威移动速度兼容字段，新客户端普通移动不消费。
- `correction_ignore_distance`：本机预测误差可直接忽略的最大距离，由数据库移动配置派生。
- `correction_snap_distance`：本机预测必须立即吸附的最小距离，由数据库移动配置派生。

### 5.3 `ENTITY_MOVE_PUSH`

正式启用或新增：

- `scene_version`：玩家本次进入场景的代次。
- `move_seq`：当前场景代次内单调递增的移动序号。
- `server_tick`：生成权威状态的服务端单调时间。
- `speed`：服务端随广播携带的兼容速度字段；当前普通移动链路不根据该值计算本机位置。

客户端只接收同时满足 `scene_id`、`scene_version` 和 `move_seq` 条件的新状态。该消息只服务于其他玩家视角，不会回发给移动者本机纠偏。

## 6. 数据库与地图通行数据

数据库中的地图边界和静态通行数据继续保留，用于历史能力、后台维护和出生/传送点审计；普通同场景移动当前由 Godot 客户端碰撞决定，不再经过服务端路径裁剪。

建议通过迁移新增场景导航版本表，实际字段在实施该任务时结合现有后台结构复核：

```text
world_scene_navigation
- scene_id
- version
- grid_width
- grid_height
- cell_size
- navigation_data
- status
- created_at
- updated_at
```

约束：

- 数据库是发布后导航数据的事实来源。
- Godot 工具只负责从地图资源导出通行位图并生成待执行的 SQL。
- 服务端启动时读取已发布版本到只读内存缓存。
- 后台需要提供查看、上传、发布和回滚能力。
- 动态 NPC、玩家和临时障碍不写入静态导航位图。
- 所有数据库结构变更只生成迁移 SQL，由用户执行。

## 7. PostgreSQL持久化策略

移动期间由 Redis保存客户端最近上报的位置，PostgreSQL采用以下写回策略：

| 事件 | 写回要求 |
| --- | --- |
| 持续移动 | 每 3 到 5 秒批量写回 dirty 玩家 |
| 停止移动 | 尽快异步写回 |
| 场景切换 | 必须写回或以更高版本写入新场景位置 |
| 进入战斗 | 尽力保存最近上报位置；战后本机位置由客户端本地记录恢复 |
| 断开或顶号 | 尽力同步写回并使旧会话失效 |
| 服务关闭 | 在优雅停机窗口批量刷回 |

周期写回 worker 已按 YAML 配置串行运行：默认每 5 秒使用 `SPOP` 最多领取 100 名 dirty 玩家，逐个读取 Redis 最新权威状态，并携带 `position_version` 条件写入 PostgreSQL；单玩家失败不阻断同批其他玩家，失败编号在批次末统一重新入队。数据库已有相同或更高版本时，本批状态按 stale 安全跳过，不会覆盖新位置，也不会重新入队形成无效重试。应用退出时先停止 HTTP 接入并由 Hub 关闭、等待全部 WebSocket 处理和断线回调结束，再停止周期 worker，在 5 秒窗口内有限排空 dirty 集合，最后关闭 Redis 与 PostgreSQL。排空期间失败的玩家会暂存到本轮结束后统一重入队，避免持续故障时反复领取同一玩家形成无限循环。

迁移 `123_player_position_version.sql` 定义了非负 `position_version BIGINT NOT NULL DEFAULT 0` 字段。普通档案与战斗快照读取都会恢复该版本；Redis 状态缺失时，首次进入世界以 PostgreSQL 版本作为后续移动的递增基线。周期 worker 与关键节点写回统一通过 `UpdatePositionIfNewer` 保证只有更高版本可以覆盖场景和坐标。停止移动会异步读取 Redis 最新状态写回；切图先以严格更高版本写入 PostgreSQL，再用同一版本重建 Redis；进入战斗前同步保存 Redis 中最近上报的位置，但新客户端的战后返回不读取服务端 `return_pos`；断线和顶号在后续生命周期处理前尽力同步写回；停服按 WebSocket 收口、worker 停止和 dirty 有限排空的顺序完成最终刷回。迁移已于 2026-08-17 执行；P1-09 的完整故障恢复测试仍未完成。

## 8. 客户端表现策略

### 8.1 本机玩家

- 输入后直接完成本地移动，保证移动端操作响应。
- 普通移动只上报坐标，不等待响应，也不执行平滑或立即吸附纠偏。
- 切图、复活和传送始终立即使用权威位置。
- 进入战斗前记录本地场景坐标；战斗结束后恢复该坐标，记录缺失或场景不匹配时使用地图传送出生坐标。

### 8.2 远端玩家

> 2026-10-19 实现状态：以下为已落地参数，对应 `client/scripts/feature/world/player.gd` 中的常量。

- 每个远端实体保存按发送方时间排序的快照队列，上限 32 条（`REMOTE_SNAPSHOT_BUFFER_LIMIT`）。
- 渲染时间固定落后发送方 150 毫秒（`REMOTE_INTERPOLATION_DELAY_MS`），在两个历史快照间按时间线性插值，速度与发送方本机一致。该延迟大于 100ms 上报间隔并留出网络抖动余量。
- 快照不足时允许最多 200 毫秒外推（`REMOTE_MAX_EXTRAPOLATION_MS`），之后停在最后权威位置。
- 相邻快照距离超出正常行走能力时按传送处理直接瞬移（`REMOTE_SNAP_DISTANCE_PX` = 96px 兜底），不在整张地图上滑行。
- 新快照到达导致插值目标突变时，转为按 12/秒指数衰减的视觉误差，避免肉眼可见的瞬移。
- 停止包优先：`moving=false` 的前一段保持静止，旧移动包不能覆盖新的停止状态。
- 网络移动不持续创建 Godot Tween，继续在帧循环中更新表现。
- 远端宠物不跟随网络包位置，而是逐帧采样人物插值后的画面位置记录 24px 格步路径，与本机宠物跟随逻辑一致。
- 高精度上报已移到物理帧并携带物理时钟时间戳；移动中被阻挡时按间隔补发心跳，避免观察端持续外推。

## 9. AOI演进

完成权威移动、Redis运行态和快照插值后，再根据压测数据实现网格 AOI：

- 先增加每场景在线人数、移动请求、广播包数、Redis耗时和写回失败指标。
- 按服务端场景格划分 AOI 网格，网格尺寸根据镜头范围和移动速度确定。
- 玩家跨网格时计算新旧邻域差集，分别发送进入、离开和移动事件。
- AOI可视范围至少比移动端镜头多一圈，避免屏幕边缘频繁创建和销毁。

## 13. 完成标准

本方案完成需要同时满足：

- 客户端不能通过坐标提交实现瞬移、越界或穿墙。
- Redis保存在线实时权威位置，PostgreSQL不处于每个移动包的同步关键路径。
- PostgreSQL最终位置不会被旧批次覆盖。
- 高延迟和短时抖动下，本机操作及时且远端移动连续。
- 旧场景、旧连接和旧序号消息不能覆盖新状态。
- 同场景广播规模具有指标依据，并能按需要切换到网格 AOI。
- 所有清单项、测试、协议和变更记录保持同步。
