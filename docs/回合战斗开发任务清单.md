# 回合战斗开发任务清单

本文档用于沉淀当前项目“回合战斗开发文档”的落地进度、缺口与后续实施顺序。

目标：
- 方便在重启会话后快速恢复上下文
- 明确“哪些能力已经完成、哪些只是 MVP、哪些还没有开始”
- 把后续开发拆成可以连续提交的小任务

当前适用范围：
- 适用于 `client/` Godot 客户端
- 适用于 `backend/` Go 服务端
- 默认以当前仓库现状为基础，不假设额外的战斗子系统已经存在

---

## 1. 当前完成状态

当前已完成的是：
- 服务端权威 PVE 回合战斗 MVP
- 多只己方宠物按回合收集动作并统一结算
- 第一版规则层：基础系数伤害、法力系数、当前生命比例入口、防御减伤、穿甲/易伤/格挡入口、暴击上下限
- 第一版状态层：流血、封印、眩晕、易伤、破甲、减速、暴击提升、诅咒、束缚、沉睡、麻痹、混乱
- 第一版被动层：闪避、吸血、反击、连击、复活、控制免疫
- 第一版自动托管：自动战斗开关、命令阶段截止时间、心跳驱动超时补行动、掉线后的后台托管推进
- 第一版 PVE 奖励闭环：金币、角色经验、宠物经验、文本掉落展示、`battle_record` 最小防重
- 第一版战斗真实掉落入包：当前最小 PVE 掉落已可通过 `bag` 正式落库并推送背包刷新
- 第一版断线重连恢复：`reconnect_token` 重绑、世界快照恢复、活动战斗快照恢复、最近帧补发
- 服务端最小单人 PVP 骨架：挑战、接受/拒绝、双方动作等待、结果广播
- 客户端基础战斗输入：选技能、切换敌方/友方目标、自动战斗开关、服务端倒计时展示、重连后战斗快照恢复
- 客户端最小表现层：左右阵营面板、事件横幅、文本血条、当前行动者与目标高亮

当前还没有完成的是：
- 组队 PVP
- 人物 / 宠物 / 佣兵完整共同参战
- 文档要求的完整规则层（人物/佣兵来源区分、更多属性倍率来源、更多状态/被动联动、数据驱动配置）
- 更完整的服务端托管策略（尤其是 PVP 托管策略、更细粒度调度、更长窗口补帧）
- 奖励、掉落、背包落库与失败恢复闭环
- 完整战斗站位节点与动画表现层

一句话结论：
- 现在实现的是“PVE 已可玩、PVP 已有最小服务端骨架”的阶段版，不是“完整战斗文档中的全部能力都已落地”

## 4. 推荐实施顺序

推荐顺序不是按“看起来最酷”，而是按“后面返工最少”的原则。

### 第一阶段：规则补全

先做：
- 完整伤害公式（进行中：已补基础系数合成、法力系数、有效属性倍率入口、防御减伤、穿甲/易伤/格挡入口、暴击上下限、纯固定伤害不暴击规则）
- 完整状态系统
- 被动系统

原因：
- 这是所有 PVE / PVP / 组队战斗的共同基础
- 现在先做表现层会导致后面事件类型和结果不断返工

当前阶段备注：
- `backend/server/internal/module/battle/formula.go` 已抽出独立公式层，并已接入法力系数、属性倍率入口、格挡减伤入口
- 当前服务端已打通一版“状态驱动公式”：破甲、易伤、减速、暴击提升会实际影响结算，而不再只是状态 ID 展示
- 当前服务端已补入诅咒、麻痹/束缚/沉睡、混乱等状态的权威结算入口，但还没有把所有技能和怪物配置全面铺开
- 当前服务端已补入第一批被动入口：闪避、吸血、反击，并且都在服务端结算链路中生效
- 当前服务端已补入第二批被动入口：连击、复活、控制免疫，并且都在服务端结算链路中生效
- 当前服务端已补入自动托管基础能力：自动战斗开关、命令阶段服务端截止时间、心跳驱动的超时自动补行动、掉线/心跳失联后的后台托管推进
- 当前服务端已补入第一版 PVE 奖励闭环：金币、角色经验、宠物经验、文本掉落展示以及 `battle_record` 去重记录；客户端也能收到奖励摘要并刷新本地玩家数据
- 当前服务端已补入第一版战斗真实掉落入包：PVE 胜利后会把最小掉落道具正式发入 `bag`，并复用背包推送刷新
- 当前服务端已补入敌方全体技能与指定数量多目标技能，客户端也会按 `target_type` 展示对应目标徽标并约束按钮交互
- 当前服务端已补入第一版断线重连恢复：短时会话保留、`reconnect_token` 重绑、新连接恢复世界全量快照与活动战斗快照；客户端也会优先尝试自动重连
- 当前已补入最小版最近帧补发：客户端可上报 `last_frame`，服务端会在缓存窗口内返回 `battle_replay_states`，让重连后不会只拿到当前状态
- 当前服务端已补入最小版单人 PVP：支持挑战请求、接受/拒绝、双方共用同一权威战斗状态和统一结果广播
- 当前仍未完成“人物/佣兵来源区分的格挡、全量属性倍率来源、更多状态与被动联动、数据驱动被动配置、复活/连击的更复杂边界、PVP 托管策略、更完整掉落/背包闭环、更长窗口/逐事件级战斗补帧重连与更细粒度调度器”等文档全量规则，后续应继续在公式层和状态系统之间打通

### 第二阶段：服务端权威托管

再做：
- 更细粒度的服务端自动战斗策略
- 完整回合命令缓冲

原因：
- 以后 PVP 一定依赖它
- 现在 PVE 已经有服务端截止时间、心跳驱动补行动和掉线后的后台托管，但还没有覆盖 PVP 与更复杂的托管规则

### 第三阶段：PVE 完整闭环

再做：
- 奖励发放
- 掉落生成
- 失败处理
- 持久化记录

原因：
- 这会把当前 PVE 从“能打”升级成“能玩”

### 第四阶段：客户端战斗表现层

再做：
- 真正战斗站位
- 单位卡组件
- 飘字
- 状态图标
- 轻量动效

原因：
- 此时服务端事件结构更稳定，客户端不容易反复返工

### 第五阶段：PVP

最后做：
- 单人 PVP
- 组队 PVP

原因：
- 这部分最依赖前面四个阶段已经稳定
